# YourPay integration

Use the bundled `yourpay` CLI. Its commands emit JSON. Read `yourpay help` to discover commands; `yourpay init --dry-run` identifies supported frameworks and previews files. Use the actual deployed API origin supplied by the user or existing server configuration; do not invent a production domain or assume the npm packages have been published.

When installed in the website project from a PayCryptoKit download, run commands as `npx --no-install yourpay ...` from that project. Do not let npx fetch a similarly named registry package. The direct-download SDK and CLI keep their existing `@yourpay/*` package names for compatibility. Downloaded development previews do not enable live payments.

## Connect the website

Start with `yourpay connect --offline` in the website project; for a BTC/LTC integration use `yourpay connect --native --offline` instead. Its unified report contains framework detection, bounded business-code filename hints, scaffold preview, missing server variables, diagnostics and a next action. Inspect the suggested authentication/order/database/fulfillment files: filenames are clues, not evidence that the hooks are implemented. Apply the reviewed adapter with `yourpay connect --apply --offline`, retaining `--native` for BTC/LTC; repeated runs preserve existing files. An existing scaffold may still be partial and must be inspected. After server configuration is available, run `yourpay connect` for online diagnostics.

The report distinguishes diagnostics from tests that have not run. Do not turn `diagnostics: passed` into successful integration: application fulfillment and public payment remain unverified until separately exercised. Review the discovered project scripts and use `yourpay connect --check typecheck,test,build` for selected existing checks; `test:e2e` is also supported. Script execution is explicit, sequential and stops on failure or a two-minute timeout. Results contain exit codes and durations, not potentially secret-bearing logs. Failed checks exit the CLI nonzero; inspect them locally. Passing a generic test script does not establish payment-specific coverage. Follow the report's missing configuration steps. Browser CLI login does not configure the website environment or create its webhook secret.

Inspect the existing authentication, order/pricing service, database and fulfillment flow first. Preserve its source of truth. Use `yourpay login --url <origin>` for device authorization when credentials are missing. The user opens the returned connection link, verifies the code matches the requesting AI/terminal, confirms their identity and explicitly approves the connection. Return to the AI/CLI afterward; entering the merchant dashboard is not required. Reuse valid saved credentials instead of asking the user to sign in repeatedly. Never request wallet private keys.

For deployments supporting `identityFamily`, the merchant can sign in with EVM, TRON or Solana. A new store uses that same wallet as its first receiving address; the sign-in message explicitly authorizes this initial binding. Returning users must use their original identity wallet: switching families creates a separate store, not an account link. Existing receiver settings survive repeated login. Check the actual deployment before promising these capabilities; older deployments require EVM sign-in.

Ask which networks the merchant wants to offer and start with their existing receiving addresses. Read `/api/merchant` for configured receiving wallets and `/api/networks` for configured network/asset pairs. Offer only their intersection and the merchant's intended selection. One EVM address covers enabled EVM networks; a TRON/Solana identity is never an EVM destination. The EVM identity wallet is a legacy default only when `identityFamily` is EVM (or absent on an older deployment).

On deployments supporting receiver review, use `yourpay receiver-review --family evm|tron|solana --address ADDRESS` or MCP `yourpay_review_receiving_address` to create a dedicated review link. The merchant confirms the exact destination with their existing store identity; they need not connect the receiving wallet. A link alone changes nothing. After approval, run `yourpay receiver-status` or MCP `yourpay_receiving_addresses` and compare the persisted family/address to the intended value before configuring future orders. This readback is not payment or channel-readiness evidence. Do not use this EVM/TRON/Solana flow for BTC/LTC branches.

On deployments with the address-first Settings form, the merchant can paste an EVM, Solana or TRON address and approve the exact destination with the existing merchant identity account. The receiving wallet need not connect or sign. A saved `verificationMethod: merchant_authorized` address has `authorizedAt` and a null `verifiedAt`: do not call it verified wallet ownership. Optional receiving-wallet signatures remain available. Older deployments still require both signatures; inspect the actual Settings form before promising address-only setup. Do not use an API key to modify receiving wallets, bypass the account confirmation, or ask the user to send a seed/private key. Existing invoices retain their original destination; additional addresses affect future orders. BTC/LTC still use the public-branch flow below, not an arbitrary pasted address.

Before a purchase test, explain and check service credit: customer funds go to the receiving wallet, while the 0.2% service fee is reserved and charged from a separate merchant prepaid balance. The current minimum top-up is 5 stablecoin units. Network fees are paid by the customer's wallet and are separate; incoming gas does not pay a subsequent forwarding transaction. Do not enable live EVM/TRON forwarding to work around missing gas funding. Start with the available verified direct-payment channels and keep unavailable channels closed.

For Next.js App Router, run `yourpay init --dry-run`, inspect the plan and existing paths, then run `yourpay init`. The CLI never overwrites existing integration files. Other frameworks use `@yourpay/sdk` from their server-side request handlers; follow the same trust boundaries below. Install the SDK from the user's supplied release or the registry only if that package is actually published and verified.

For stable-token templates, implement the generated `resolveOrder` and `fulfillPayment` hooks. They deliberately fail until business logic is connected. `resolveOrder` must authenticate the customer, verify access to the order, and obtain price, currency and network from server-side configuration. Do not pass browser-supplied prices or recipient addresses through to the payment API. Repeated create attempts for one order use the same `orderId` and parameters. Native hooks are described below.

To offer customer choice, persist `paymentOptions` with the local order, including its default network/asset, and send that saved list to `createInvoice`. All offered stablecoins use the same nominal amount; do not invent conversion rates. The checkout locks one network/token before signing, so changes after payment starts are unavailable. Creation retries use the original saved parameters even when the response reflects a customer's different selection.

In `fulfillPayment`, verify the event against the local order's amount and either its fixed asset/network or its persisted allowed pairs. Never trust an event's offered list as the business authorization source. Claim `event.id` using a database uniqueness constraint and grant the entitlement in the SAME durable transaction. A duplicate event is a successful no-op. Never implement fulfillment as console logging or an in-memory Set. Nontransactional side effects require a durable outbox. Transient errors must return a non-2xx response so delivery retries.

Store `YOURPAY_API_URL`, `YOURPAY_API_KEY` and `YOURPAY_WEBHOOK_SECRET` in server-only environment configuration. Never use `NEXT_PUBLIC_` for secrets or commit them. Verify the webhook using the exact raw request text and `yourpay-signature`; keep the five-minute signature window. A completion message from the checkout only updates the UI and cannot authorize fulfillment.

Add the purchase button to the actual purchase flow. Hosted checkout works in wallet browsers; use `@yourpay/sdk/browser` for a modal only after testing injected wallet availability inside the iframe. Register the merchant website origin and public HTTPS callback URL using the configuration flow below when the deployment supports it. Device login alone does not register settings. The merchant console is optional. Only show configured, merchant-enabled networks returned by `/api/networks`; roadmap entries are not payment options. Network fees are separate from the 0.2% service fee. Test and live deployments have separate databases and credits.

## Configure through AI

For deployments supporting settings requests, save a JSON file containing exactly `name`, `appUrl`, and `webhookUrl`. Derive the URLs from the reviewed website deployment and implemented callback; do not invent a destination. Explicit `null` removes a URL. Use `yourpay settings-request --input FILE` (or MCP `yourpay_request_settings`) to propose these values. Present the returned approval link to the merchant for authenticated review, then return to the conversation. The AI must not approve on their behalf or substitute an API key for owner consent. `settings-poll --id UUID` uses the original requesting credential and consumes an approved status once.

For initial Webhook secret setup, first check the project has no conflicting payment variables. Run `yourpay settings-request --input FILE --rotate-webhook-secret`. Keep both returned public identifiers, `id` and `deliveryKeyId`, plus the key fingerprint. The merchant reviews the exact settings and separately confirms secret replacement. Then run `yourpay settings-deliver --id REQUEST_UUID --delivery-key-id LOCAL_KEY_UUID --cwd PROJECT_PATH` on the same computer under the same OS user and CLI credential. This decrypts directly into `.env.local`; do not read private key files or print decrypted configuration into the conversation. MCP `yourpay_settings_delivery` can inspect ciphertext availability, but cannot install the local configuration.

Retry delivery using those same IDs until the ten-minute request expiry, even after status polling was consumed. Identical local configuration returns `already_configured`; missing variables are added while unrelated values remain intact. Existing conflicting payment values require coordinated migration, not automatic overwrite. Never automatically recreate a request after an uncertain response or missing key: a previous approval may already have changed the hosted secret. Do not rotate an existing working integration just to discover its secret. Updating an existing integration also requires deploying matching server configuration and accounting for queued events signed with the old secret; local delivery alone does not complete that migration. If the deployed API lacks these endpoints, report that compatibility gap instead of claiming the newer package upgraded the service.

## Native BTC/LTC integration

For BTC/LTC, use the separate native quote and invoice APIs. On a fresh Next.js integration, `connect --native` or `init --native` generates the native template. Default templates remain stable-token-only. Existing files are never migrated by switching the flag. If the user requires both native coins and stable tokens, integrate both server flows explicitly into their business model rather than silently choosing one; the generated single-flow route does not combine them.

Implement `resolveNativeOrder` to authenticate and load the server order with its already persisted quote request UUID. Implement `saveNativeQuote` to atomically save the quote snapshot and immutable acceptance options, returning the same options on concurrent retries. Implement `saveNativeInvoice` to attach the accepted invoice ID idempotently and reject conflicting IDs. The generated route returns checkout only after this save completes; failure must recover using the original quote/request/options. Implement `fulfillPayment` against the saved native snapshot. Do not reject an expired quote before attempting recovery of an already accepted invoice; the service checks expiry for new acceptance. Deliberate requoting is a separate business decision after reconciliation.

Discover exact native network IDs in `yourpay networks` → `nativeNetworks`; `invoiceApiEnabled: true` is configuration, not proof of healthy monitoring or merchant eligibility. Native hosted checkout, wallet-request links and both QR modes are implemented, with local Core/browser evidence. External wallet-app interoperability and public-network acceptance remain unfinished. Keep customer-facing native options unavailable until the deployment gates pass. Do not enable operator network settings merely to make an integration test pass.

The merchant connects a dedicated public receiving branch through Settings and proves control with the native wallet and merchant identity signatures. The platform and AI must not receive the seed or private key. The current browser flow uses manual native signatures; do not describe it as automatic wallet-app integration. A public descriptor is sufficient to derive receiving addresses, but exposes account activity and should stay in authenticated setup.

Persist a quote request UUID, order ID, configured network, denomination (`USD` or `native`) and decimal-string amount in the merchant database. Use SDK `createNativeQuote` or `yourpay native-quote --input FILE`. Save the returned quote ID and snapshot. Rates and confirmations come from the service, not the buyer. Use `getNativeQuote` / `native-quote-get --id UUID` to inspect the saved quote.

Accept with SDK `createNativeInvoice({quoteId,title,returnUrl?,paymentWindowSeconds?})` or `yourpay native-invoice --input FILE`. On an uncertain response, retry the same persisted acceptance parameters or recover using `getInvoice` / `invoice-get --id UUID` and merchant invoice history. Never silently generate a fresh UUID or accept a new price after failure. A deliberately refreshed quote requires a new saved request UUID, after checking that the earlier acceptance did not already create an invoice. Quote expiry and invoice payment expiry are different deadlines.

Match a native completion event to the saved invoice's native atomic amount, BTC/LTC asset, network and local authenticated order. A USD order price is not the native transfer amount. Preserve the shared raw-body signature verification and transactional fulfillment rules. Report price-source failure, unavailable worker readiness or insufficient service credit as actionable setup/runtime errors rather than replacing the rate or bypassing checks.

For receipt investigation, use `yourpay invoice-get --id UUID` for monitoring/hold context, then `yourpay native-receipts --id UUID --limit 50`. Pass each returned `nextCursor` unchanged through `--before` until null; retry a failed page with the same cursor. These are recorded observations, not proof of current finality or permission to deliver/refund. Keep atomic amounts as integers, identify outputs by transaction hash plus output index, and restart at the first page when checking for newly discovered evidence. Never sum an already loaded page twice or clear a chain hold to resume checkout.

## Verify the outcome

Run `yourpay doctor`. In local development, `yourpay listen --forward-to http://localhost:<port>/api/yourpay/webhook` polls the TEST deployment and signs forwarded events with `YOURPAY_LISTEN_SECRET`, which must match the local website's webhook secret. It does not acknowledge hosted deliveries.

Verify a complete purchase, an unauthenticated order attempt, a tampered price, an invalid webhook signature, duplicate deliveries, and a transient fulfillment failure followed by a retry. Confirm the actual purchased entitlement is persisted once. Report unfinished hooks, unavailable networks and unconfigured deployment dependencies explicitly; scaffold generation alone is not completed integration.

When the existing Webhook secret is already available in the local environment, `yourpay connect --configure-env --offline` configures server-only `.env.local` from saved login (or a complete API URL/key environment pair) and YOURPAY_WEBHOOK_SECRET. It creates the file or adds missing variables and accepts identical retries. Never invent a secret and assume the hosted endpoint shares it. No secret belongs in CLI arguments or agent output. Conflicting payment values and tracked credential paths are preserved. This configures the local website only; configure and verify production hosting separately before claiming the website is connected.
